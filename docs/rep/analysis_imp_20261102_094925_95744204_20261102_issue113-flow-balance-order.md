## 1. Change under test

`NetworkImputer._build_flow_balances` visits its flow balances in `sorted(by_to.keys() & by_from.keys())` order
(`0d49c45`, merged in `1848a90`), not in the order of a set of `(node_id, time)` tuples whose string hashes Python
seeds per process. The hash-seed test (`tests/test_network_imputer.py`) already checks that the list is the same under
`PYTHONHASHSEED` 0, 1 and 2. This measurement checks the stored run.

The issue names `imp_20261021_125954_b112b170` as the reference. #111 moved the reference chain after #113 was filed,
and #108's sweep compares its points with the new chain, so the measurement uses the new chain's imp run. The
pre-registration comment on #113 states the switch.

## 2. Decision items

Pre-registered on #113 (2026-11-02) and in the docstring of `scripts/explo/issue113_flow_balance_order_diag.py`
before either run started.

## 4. What this does not show

The measurement shows that no value of the copper chain depends on the order of the flow balances. It does not show
that no input could make it matter, for instance two balances that could fill the same edge first. Since `0d49c45` the
question no longer reaches a run: every process visits the balances in one order, so an order effect, if one existed,
would be the same in every point of a sweep.
